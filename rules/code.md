# Код — обязательные требования

Это требования, а не пожелания. Свод живёт отдельным файлом ради читаемости: длинное
always-loaded полотно читается хуже короткого. Фронтматтера `paths:` здесь нет намеренно — на
user-скоупе он не «включает файл по путям», а молча выключает его во всех проектах.

При конфликте с правилом `01-a-working-product` побеждает `01-a-working-product`. Простота не
отменяет полноту, безопасность, data integrity, обработку достижимых отказов и проверку продукта.
Краткость — тайбрейк ПРИ РАВНОМ качестве, а не право оставить кривое.

## Простота

Сначала запиши мысленный baseline: самый прямой вариант, который **полностью** решает задачу и
сохраняет известные инварианты. Не нарочно плохой и не урезанный happy path. Усложняй его только
под существующее давление.

Каждая новая сущность платит за существование: слой, abstraction, configurable branch,
dependency, state field, public contract или generalization должны закрывать конкретное текущее
требование, доказанный инвариант либо известную нормальную эволюцию. Не можешь назвать основание —
удали. Строго доминирующее решение проще и сохраняет все доказанные свойства; оно обязательно.

Лестница reuse/buy-before-build — остановись на первой ступени, которая держит все свойства:

1. Нужно ли это вообще? Спекулятивная надобность — не делай, скажи одной строкой.
2. Уже есть в репозитории (хелпер, util, тип, паттерн)? Переиспользуй. Переписывать своё то, что
   лежит парой файлов рядом, — главный источник мусора.
3. Stdlib решает? Бери stdlib.
4. Нативная фича платформы? `<input type="date">` вместо пикер-либы, CSS вместо JS, constraint БД
   вместо кода в приложении.
5. Уже установленная зависимость? Бери её, если её контракт подходит.
6. Только теперь — минимальный собственный механизм.

- Удаляй охотнее, чем добавляй. Скучное лучше умного: умное разбирают в три ночи.
- Держи минимум понятий, состояния, зависимостей, публичных контрактов, файлов и ветвей. LOC —
  слабая метрика: тридцать прямых строк часто дешевле двенадцати вокруг factory и generics.
- Запрещено: интерфейс с одной реализацией, фабрика на один продукт, конфиг под значение, которое
  не меняется между средами/запусками, скаффолдинг «на потом» — если нет другого текущего давления.
- Лестница сокращает **решение**, а не **чтение**: сперва пройди весь путь кода, который правишь,
  и только потом упрощай. Маленький диф не в том месте — это второй баг, а не экономия.
- Осознанно срезал угол с известным потолком (глобальный лок, O(n²), наивная эвристика) — пометь
  комментарием с потолком и путём апгрейда.
- Баг чини в корне: перед правкой найди всех вызывающих. Один гард в общей функции — диф меньше,
  чем гард в каждом вызове, и чинит соседние пути тоже.
- Нетривиальная логика (ветка, цикл, парсер, деньги, безопасность) без чека не сделана: оставь
  один запускаемый чек — `assert`-based `demo()`/`__main__` или один `test_*`. Тривиальный
  однострочник тестами не обвешивай.
- Никогда не упрощай: валидацию на границах доверия, обработку ошибок, спасающую данные,
  безопасность, базовую доступность, явно запрошенное человеком.

## Архитектура

- Сначала следуй архитектуре репозитория. Не вводи глобальную схему
  `transport/service/domain/repo/util` в проект, где такого разделения нет.
- Новый слой, модуль или interface оправдан, когда уже есть реальное давление: две различающиеся
  реализации; duplication с риском divergence; trust/IO boundary; independent lifecycle;
  состояние со своими invariants; либо модуль уже смешивает независимо меняющиеся причины.
- Нет давления — оставь прямую локальную реализацию. Один handler с восемью строками логики часто
  честнее, чем service + interface + factory + DTO + mapper.
- Границы, направление зависимостей и запрет reach-through/cycles — §32-boundary-integrity.
- Публичный API минимален: экспортируй только то, что сегодня имеет внешнего потребителя.

## Функции

- Функция делает одну связную операцию на одном уровне абстракции. Делить её надо при независимой
  причине изменения, повторном использовании или когда название больше не описывает всё тело.
- Pure core полезен, когда отделяет существенную логику от IO и упрощает проверку. Тривиальную
  оболочку не раскладывай на impure/pure/impure ради паттерна.
- Параметры объединяй в именованный объект, когда они образуют понятие, часто меняются вместе или
  позиционный вызов становится неоднозначным. Не создавай DTO ради одного короткого вызова.
- Flag-параметр разделяй, только если он выбирает две разные операции; опция одной операции может
  оставаться опцией.
- Возврат соответствует контракту проекта. `unknown` сужай на границе; `any` не протаскивай.
  `null` допустим как реальное отсутствие, но не как скрытая потеря ошибки.
- Глубокую вложенность и смешение парсинга, бизнес-правил и persistence упрощай, если они уже
  мешают отдельно понять, проверить или изменить эти части.

## Именование

- Функции — глагол: `parseInput`, `fetchUser`, `validateOrder`. Запрещены `process`, `handle`,
  `doStuff`, `run` без объекта.
- Предикаты `is*`/`has*`/`can*`/`should*` возвращают boolean: `isAdmin`, `hasPermission`, не
  `admin`.
- Булевы переменные только `is*`/`has*`/`should*`/`can*`: `active` → `isActive`.
- Коллекции во множественном числе: `users`, `orderItems`. Не `userList`, `userArr`, `userData`.
- Map и словарь — `*ById`/`*ByKey`/`*Map`: `usersById`, не `userMap`.
- В циклах `i`/`j` для индексов, `user`/`item` для элементов. Не `theUser`, не `usr`.
- Константы UPPER_SNAKE для enum и магических чисел (`MAX_RETRIES`, `STATUS_ACTIVE`);
  runtime-конфиг — в env или config, не в коде.
- Файлы kebab-case (`user-service.ts`); PascalCase — только React-компоненты и файлы-классы;
  snake_case — только Python. Модули kebab-case или short-lowercase.
- Длина имени пропорциональна области видимости: локальная `i` — нормально, публичный аргумент
  `userId`, глобальный конфиг `MAX_CONCURRENT_CONNECTIONS`.
- Двойные отрицания запрещены: `isNotDisabled` → `isEnabled`.

## Ошибки

- Запрещено `throw "msg"` — теряет stack, тип и контекст, не ловится через instanceof.
- Запрещено `catch (e) { return null }` — подавление даёт тихий баг. Пробрось или обработай: лог и
  rethrow с `cause` либо верни явный ожидаемый outcome по контракту проекта.
- Обработка ошибок, контракты и поведение на границе — §34-failure-is-not-default.

## Side effects

- Изолируй IO, время, randomness и мутацию, когда от них зависит бизнес-правило, повторяемость
  проверки, транзакционная граница или замена реальной инфраструктуры.
- Внедряй clock/RNG/file reader/db/client только при таком seam или когда этого требует
  существующая архитектура. Не передавай `now()` через пять слоёв, если время читается один раз в
  entrypoint и не влияет на решение.
- Функция, обещающая быть pure, не мутирует аргументы: `arr.sort()` требует осознанной копии либо
  явного mutating-контракта.
- `console.log` в проде — баг, используй logger с уровнями.
- Эффект именуй по действию (`readConfig`, `sendEmail`, `commitTransaction`), чтобы вызывающий видел
  boundary без чтения тела.

## Антипаттерны

«Это маленький скрипт» не аргумент.

- Entrypoint/handler должен оставаться обозримым. Выноси бизнес-логику, когда она переиспользуется,
  имеет собственные invariants или мешает увидеть boundary; не создавай service ради одной ветки.
- God-объект разделяй по независимо меняющимся обязанностям, а не механически по размеру.
- Global mutable state запрещён, когда несёт request/user state, ломает изоляцию или создаёт
  неявный lifecycle. Неизменяемая module-level константа и управляемый process-wide cache — другой
  контракт, их не маскируй под DI без причины.
- Нет monkey-patching и мутаций `Object.prototype`/`Function.prototype`: расширяй наследованием
  или композицией.
- Copy-paste выноси, когда копии представляют один invariant и могут разъехаться. Совпали control
  flow, порядок эффектов, validation или lifecycle, а отличаются только schema/prompt/policy — это
  один механизм с передаваемым контрактом. Два похожих, но независимо меняющихся фрагмента не
  объединяй преждевременно.
- Повторяемое или меняющееся значение имеет имя и один источник истины. Одно локальное значение с
  очевидным смыслом не требует каталога констант.
- Branch chain заменяй таблицей/полиморфизмом, когда ветви образуют стабильное отображение или уже
  меняются независимо; короткий явный `if` лучше косвенной диспетчеризации.

## Комментарии

- Комментарий объясняет **почему**, а не **что**. Пересказ кода — мусор, код читается сам.
- Комментируй инварианты, контракты, неочевидные trade-off, предупреждения («не менять порядок
  полей — сломается сериализация»).
- TODO, FIXME, HACK — только с причиной и ссылкой на задачу.
- Документируй экспортируемый контракт, если имя и типы не объясняют важные гарантии, эффекты или
  исключения. Не дублируй сигнатуру шаблонным docstring.
- Запрещено комментировать очевидное — переименуй переменную или функцию.
- Запрещено оставлять врущий комментарий: изменил код — обнови комментарий.
- Запрещено оставлять закомментированный код — удаляй, история в гите.

## Данные и состояние

- Один факт — один источник истины. Выводимое не дублируй состоянием; кешируешь — назови
  синхронизацию и инвалидацию.
- Число о данных вычисляй из источника, а не вписывай снимком. Задают снаружи — конфиг; следует из
  данных — вычисляй. Дата как условие работы — таймер самоуничтожения.
- Данные считай неограниченными, пока лимит не доказан: прогони объём x10 и x100 — память, время,
  запросы, размер, лимиты API. Растущее без retention — баг.

## Многошаговое и параллельное

- Многошаговый механизм — состояния и переходы, а не набор `if`. Назови состояния, переходы,
  повторный вход, конечное состояние и продолжение после падения.
- Считай процесс прерванным на любой строке: что уже изменилось, что нет, можно ли повторить, как
  узнать о выполненном. Падение не должно оставлять неопределённое состояние.
- Нет гарантии одного исполнителя — считай, что их два. Проверка в коде не заменяет ограничение в
  хранилище: атомарная операция, constraint, транзакция, CAS.
- Может сломаться без падения — сделай видимым: последний успех, объём работы, остаток, последняя
  ошибка. Тихая деградация хуже явного падения.

## Безопасность

- Секреты не в коде и не в логах. Вход снаружи недоверенный. Инъекции лечатся конструкцией
  (параметризация, экранирование на границе), а не фильтром на входе.
- Право на объект проверяется на каждом действии, а не один раз при входе.
- Отключение проверки — не фикс.

## Проверка и гит

- Прогони тесты, typecheck и линт по затронутым файлам до завершения. Зелёный — только после
  реального прогона; доказательство — команда и её вывод.
- Проверяй по типу работы: HTTP — curl сам; вёрстка — скриншот и инспектор; UI — прокликать;
  CLI — вход и exit code; БД — SELECT после записи; сборка — запуск артефакта.
- Ошибка тула означает, что неверна твоя модель мира: повтор с теми же аргументами — баг. После
  неудачной правки перечитай файл. Файлы правь нативными тулами, а не скриптами.
- Страховка — коммит, а не `.bak` рядом с файлом. Коммить осмысленными порциями с причиной;
  индексируй пути своей работы, а не всё дерево. Секреты — в `.gitignore` тем же диффом.
