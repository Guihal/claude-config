# TZ — оформление технического задания

Юзер кидает сырьё. Агент оформляет ТЗ. Старт — по явному сигналу юзера;
gap-секция не блокирует исполнение.

## Принцип направления

**Юзер не оформляет — юзер кидает сырьё.** Любой формы: текст, куски, ссылки,
файлы, контекст, несколько сообщений подряд. Всю работу по структуре делает
агент. Юзер только отвечает на подсвеченные пробелы.

## Поток

1. **Приём сырья.** Без вопросов «в каком формате». Берём как есть.
2. **Самооформление.** Маппим сырьё на блоки структуры (ниже). Что недосказано —
   выводим из контекста и помечаем `[предположил: X, из <какая часть сырья/сообщения юзера>]`.
   Лучше обоснованное предположение с источником, чем пустое поле или `TBD`.
3. **Gap-секция.** В конец ТЗ — список `⚠️ Не хватает / неясно`: конкретные
   пробелы одним пакетом, не по одному вопросу.
4. **Дофинализация.** Юзер отвечает на дыры → вшиваем → обновляем ТЗ + gap.
   Повторяем, пока gap не пуст или юзер не скажет старт.
5. **Старт.** См. «Механика старта».

## Механика старта

ТЗ считается готовым к передаче в `task` только по явному сигналу юзера.
Gap-секция НЕ блокирует: нерешённые пункты остаются списком неясностей
(с `[предположил: X, из <источник>]`), открытые вопросы уходят в кристалл §2
Open questions при передаче в `task`.

**Явный старт:** `стартуем`, `го`, `погнали`, `запускай`, `начинай`, `/go`.
**НЕ старт** (даже если звучит позитивно): `ок`, `давай`, `продолжай`, ответы
на дыры, уточняющие вопросы. Если неявно — переспросить один раз, не двигаться.

**Force-close** (`забей на X` / `skip X` / `принимаем как есть`) — инструмент
вычёркивания пункта: X уходит из gap (или в non-goals / assumptions) и больше
не является вопросом к юзеру.

## Адаптация по сложности

Если ввод начинается с `--depth=trivial|standard|complex` — override, убрать из
текста. Иначе классифицируем:

| depth | когда | блоки |
|---|---|---|
| trivial | мелкая правка, один файл, очевидно | цель, результат, non-goals, приёмка, **gap** |
| standard | обычный фича/багфикс | полный вариант A |
| complex | архитектура, рефактор, пайплайн, безопасность, data-flow | A + `--full` |

Когда сомневаемся — `standard`. Флаг `--full` форсирует расширенный набор B.

**Gap-секция действует на ВСЕ уровни, включая trivial** (список неясностей
с источниками). Старт — по явному сигналу юзера; gap не блокирует ни на одном
уровне.

## Архитектурный подход (выбор)

Для архитектурных задач агент ВЫБИРАЕТ подход явно и фиксирует в ТЗ
(в плане/кристалле). Каталог (на основе правил code-architecture):

| Тип задачи | Подход |
|---|---|
| CRUD / API | layered: transport / service / domain / repo |
| ETL / пайплайн / data-flow | pipeline stages + очередь |
| CLI-инструмент | entry + core + adapters |
| Библиотека | pure core + thin API |
| Веб-интерфейс | компоненты + токены (ui-стандарты) |
| Рефактор | изоляция слоёв без изменения наблюдаемого поведения |

Код в ТЗ НЕ пишется (см. Принципы). Кодовая правка >10 строк → использовать
`tz`; для архитектурных задач tz-механика доступна из task-скиллов.

## Структура ТЗ

### Вариант A (standard, по умолчанию)

1. **Контекст / зачем** — какая проблема, мотивация. Решает «а надо ли это».
2. **Цель** — одно побудительное предложение, без оценочных прилагательных
   («правильно»/«чисто»/«эффективно»).
3. **Ожидаемый результат** — конкретный артефакт (файл, сервис, поведение).
4. **Scope** — что входит + **non-goals (минимум 3 конкретных запрета, каждый с `INVARIANT:`-тегом — см. принципы)**.
5. **Требования (функциональные)** — что система должна делать.
6. **Критерии приёмки** — проверяемые: команды с exit-кодами, если есть CLI;
   иначе чёткие проверяемые условия. Никаких «работает корректно».
7. **План / этапы** — последовательность шагов к результату.
8. **⚠️ Gap-секция** — `Не хватает / неясно` + что предположил.

### Вариант B (`--full` или complex)

К A добавляются:

- **Нефункциональные требования** — производительность, безопасность,
  доступность, наблюдаемость.
- **Риски** — что может пойти не так + митигация.
- **Risk tier** — `ordinary | public-api | schema | db | security`.
- **Бюджет** — `diff_budget_loc`, `file_count_max` (опц., ориентир для исполнителя).
- **Глоссарий** — термины проекта (для однозначности).
- **Откат (rollback)** — одно предложение, как откатить изменение.
- **Окружение / зависимости** — стек, версии, смежные системы.

## Принципы хорошего ТЗ

- **Non-goals ≥ 3** конкретных запрета («не делаем X», а не «не делаем лишнего»).
- **Запрещающие требования — с INVARIANT-тегом и негативным чеком.** Каждое
  «не делаем X» / «MUST NOT» / «без Y» / «не запускает Z» / «никогда» помечается
  `INVARIANT: <id>` (по умолчанию механизируемо → парный runnable негативный чек
  в критериях приёмки, падающий когда нарушение есть) ИЛИ
  `INVARIANT: <id> [semantic]` (только если реально немеханизируемо, с
  обоснованием). Prose-only запрет без тега/чекa = пункт в gap-секции
  (constitution I3/I4; против split-scope инцидента — правило,
  написанное на пакет позже кода, никогда не бывает `+`-строкой в диффе).
- **Код в ТЗ не пишется.** Максимум 10 строк разом — только иллюстрация
  сигнатуры/интерфейса, не реализация (тот же принцип, что plan-no-code).
- **Проверяемые критерии приёмки** — runnable команды, либо чёткие условия. Не
  «матчает конвенции», а какие именно.
- **No-TBD.** Лучше `[предположил: X, из <фрагмент сырья/сообщения юзера>]`, чем пустота. Пустое поле = пробел в gap. Предположение БЕЗ источника = галлюцинация → пункт в gap (в рамках существующей gap-механики, без новой жёсткой блокировки).
- **No-choices.** Запрещены `если доступно`, `по необходимости`, `где уместно`.
  Решить или форсировать через `забей на X`.
- **Цель — побудительное предложение без прилагательных-оценок.**
- **Risk tier явный**, если в B. Не уверен → `public-api`.
- **Глоссарий** покрывает любой термин, который исполнитель может понять иначе.

## Связки с другими скиллами

- **`task`** — после явного сигнала старта запускается RLM-цикл
  plan/critic/impl. ТЗ = его входной контекст. Критерии приёмки из ТЗ =
  verify-gate для `task`; открытые вопросы gap уходят в кристалл §2 Open
  questions.

Форма — markdown. JSON-packet формат **не используется** (концепции
self-contained/runnable приняты как принципы, но не как схема).

## Финальный артефакт

Готовое ТЗ — самодостаточный markdown: читается без истории чата.
По запросу сохраняется в `docs/specs/<name>.md` или рядом с проектом
(`/usr/projects/<name>/`). Без явного запроса — только в чат.

## Анти-паттерны

- Допрашивать юзера по одному вопросу вместо пакета в gap-секции.
- Передавать в `task` без явного сигнала старта.
- Рапортовать «ТЗ готово» без явного сигнала старта.
- Пустые поля и `TBD` без пометки `[предположил]`; предположение без указания источника.
- Оценочные прилагательные в цели.
- Non-goals короче 3 или абстрактные («не делаем лишнего»).
- Запрет без `INVARIANT:`-тега и парного негативного чека (prose-only
  prohibition) — пропускает split-scope провал; такой запрет = пункт в gap-секции.
- Запрет с тегом, но без runnable негативного чека в приёмке (если не помечен
  `[semantic]` с обоснованием) — тот же дефект.
- Сохранение ТЗ в файл без явного запроса юзера.
