# Как память попадает в контекст (механика носителя)

Это единственная часть скилла `memory-curation`, которая зависит от версии Claude Code: тело
`SKILL.md` верно независимо от неё, а всё нижеследующее описывает поведение конкретного бинаря.
Поэтому каждый абзац идёт с командой перепроверки — если команда даёт другое, права команда, а
текст переписывается, а не подгоняется под старый вывод.

Какой бинарь работает сейчас:

```bash
readlink -f ~/.local/bin/claude
```

Дальше в командах он обозначен как `B="$(readlink -f ~/.local/bin/claude)"`.

## Где память включается

```bash
grep -n autoMemory ~/.claude/settings.json
```

Даёт `"autoMemoryEnabled": true` и `"autoMemoryDirectory": "~/.claude/memory"` — глобальная память
включена и лежит по этому пути. Выключатель на один запуск — переменная окружения:

```bash
strings -n 8 "$B" | grep -c CLAUDE_CODE_DISABLE_AUTO_MEMORY
```

Ненулевой ответ означает, что бинарь читает `CLAUDE_CODE_DISABLE_AUTO_MEMORY` в предикате
включения автопамяти. Отдельного тула памяти, который можно было бы запретить через
`--disallowedTools`, в бинаре нет — проверено перебором имён (`Memory`, `MemoryWrite`, `Remember`,
`AutoMemory`, `memory`): все дают «matches no known tool». Поэтому вложенный прогон, которому
нельзя писать в память, запускается именно с этой переменной, а не запретом тула.

## Два пути инжекции

Память приезжает в контекст одним из двух способов, и выбор способа — не наша настройка.

**Путь А — файл `MEMORY.md` целиком.** В контексте виден блоком
`Contents of /home/penis/.claude/memory/MEMORY.md (user's auto-memory, persists across
conversations)`. Так работает эта сессия: блок наблюдается в контексте. Суффикс
`(user's auto-memory, persists across conversations)` жёстко привязан к типу `AutoMem` в бинаре —
по нему путь А и опознаётся глазом.

**Путь Б — индекс, который CLI собирает сам** из frontmatter каждого файла каталога. Заголовок
блока и его служебный маркер:

```bash
strings -n 6 "$B" | grep -o 'Memory files under .\{0,50\}' | head -2
strings -n 6 "$B" | grep -nx "<auto-memory-index>"
```

Что делает сборка — читается в теле функции, которая строит запись индекса:

```bash
strings -n 200 "$B" | grep -o '.\{500\}pinnedState:.\{200\}' | head -2
```

В выводе видно:

- в индекс идут файлы `*.md` каталога памяти, а сам `MEMORY.md` из него исключён (`basename(c)!=="MEMORY.md"`);
- запись индекса — `description` из frontmatter, а если его нет — начало тела или вовсе пусто (`f.description ?? (o ? Q$p(m) : null)`, где `o` включается только при loaded-index-exclusions): файл без внятного `description` попадает в индекс безымянным огрызком или без пояснения вовсе;
- порядок — по времени модификации файла: сборка сортирует `.sort((c,u)=>u.mtimeMs-c.mtimeMs)`, свежие первыми (ключ — `mtimeMs`, не `metadata.modified`);
- `metadata.type` нормализуется отдельной функцией — отсюда набор `reference` / `feedback` / `project` / `user`;
- у собираемого индекса есть верхняя граница по числу файлов: список файлов памяти режется в сборщике `.slice(0,J4v)`. Значение — снимком тут не лежит, читается командой:

  ```bash
  strings -n 8 "$B" | grep -oE 'J4v=[0-9]+'
  ```

  На этом бинаре даёт `J4v=200` (в индекс попадают 200 файлов; при большем числе часть не видна рантайму, хотя лежит на диске). Идентификатор именно `J4v`: рядом в бинаре есть `ev_=200` из модуля поиска файлов — число совпадает случайно, читать надо константу сборщика индекса, а не любую с тем же значением. При смене версии права команда, а не это число.

**Следствие для записи факта.** Строка в `MEMORY.md` и `description` файла — два входа к одному
факту. При пути А работает первый, при пути Б — второй. Смысл у них обязан быть один, иначе при
переключении пути факт становится невидимым, хотя файл лежит на диске.

## Ссылка в индексе — это не оформление

Рантайм сам вытаскивает из индекса ссылки на файлы регулярным выражением:

```bash
strings -n 200 "$B" | grep -o 'sGv=/[^;]\{0,40\}' | head -2
```

Даёт `sGv=/\]\(([^()\n]+?\.md)\)/gi` — распознаётся ровно конструкция `](имя.md)`, а абсолютные
пути, схемы вида `http:` и `..` отбрасываются фильтром рядом. Отсюда формат строки индекса
`- [Заголовок](file.md) — суть`: имя в круглых скобках обязано совпадать с именем файла на диске,
иначе строка для рантайма ни на что не указывает.

## Pinned-файлы: тело в каждом разговоре

Механизм подтверждён в этом бинаре:

```bash
strings -n 6 "$B" | grep -n "Pinned memories (apply to every conversation)"
strings -n 6 "$B" | grep -n "pinned-memory path="
```

Ключ — `metadata.pinned` во frontmatter файла памяти: в сборке записи индекса стоит
`pinnedState: K3n(f.metadata.pinned)`, где функция возвращает `absent` / `true` / `false` /
`malformed`. Последнее — значение, которое не разбирается в boolean: такой файл не пинится, а
телеметрия отмечает его как malformed. Помеченный файл инжектится **телом** в каждый разговор,
внутри блока `# Pinned memories (apply to every conversation)`, каждый в теге
`<pinned-memory path="...">`. Сколько файлов реально инжектится, бинарь ограничивает
константой `V3n`: результат сборки пиненых режется `.slice(0,V3n)`. Значение — снимком тут не
лежит, читается командой:

```bash
strings -n 8 "$B" | grep -oE 'V3n=[0-9]+'
```

На этом бинаре даёт `V3n=4`, то есть инжектится не больше 4 пиненых файлов; при превышении бинарь
шлёт телеметрию `memory_pinned_inject` / `cap_dropped`, и лишние (самые старые по `modifiedMs` —
кандидаты сортируются `toSorted` по нему) молча не
приезжают. Осторожно с соседней `X4v` (=`V3n*2`): она режет только промежуточный список
кандидатов, а не то, что уходит в контекст, — эффективный кап это `V3n`. При смене версии права
команда, а не это число.

**Что из этого следует для решения.** Pin — это не «важный факт», а перевод файла в разряд того,
что действует всегда. По § Куда именно такое обычно и есть поведенческий слой (`AGENTS.md`,
`rules/`), а не память: пин делает то же самое, но мимо места, где живут постоянные правила, и мимо
бюджета инжекции, который там считается. Поэтому пин — решение уровня поведенческого правила, а не
способ подсветить любимый факт.

## Память под гитом

```bash
git -C ~/.claude log --oneline -- memory | head
git -C ~/.claude status --porcelain memory
```

История правок памяти лежит в гите: у любого факта видно, когда и каким изменением он появился.
Это делает удаление протухшего факта дешёвым — терять нечего — и даёт способ ответить на вопрос
«откуда вообще взялась эта строка». Вторая команда проверяет, не записал ли чего в память вложенный
прогон: пустой вывод — ничего не записано.
